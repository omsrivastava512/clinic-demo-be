## Axis 1 — where the write happens

The schema's one consistent rule — derive_owner_id_from_patient overwriting whatever owner_id a client sends, validate_owner_is_admin refusing a non-admin owner_id, process_new_complaint_course checking cross-chain tenancy itself because SECURITY DEFINER means RLS isn't watching, invoice_number never coming from the client — is that anything following a fixed rule from context gets derived or validated server-side, never trusted verbatim. That's the yardstick here.

Before comparing the three options, I need to be precise about something specialty-decision-log.md already settled, because it looks at first glance like it answers this axis and it doesn't, quite. Entry 13 chose a deferred constraint trigger over "a SECURITY DEFINER stored-procedure/RPC alternative... blocking direct table writes" to guard invoice_line_items integrity, specifically for "consistency with this schema's existing idiom — every other guard in this project is a trigger reacting to a write, never a restricted RPC clients must call instead." That's real and settled, and I'm not reopening it — validation for "does this invoice have line items, do they sum correctly" stays a trigger, fires no matter how the write arrives. But that's a different question from what this axis is asking, which is how the client issues the write, not what checks it once it lands. And there's a structural fact worth naming plainly: a deferred constraint trigger only does anything a normal trigger doesn't when there are multiple statements sharing one transaction for it to wait out — check it at the end of a single-statement transaction and it fires at essentially the same moment a normal trigger would. For Entry 13's check to ever see both the invoice row and its line items before deciding pass or fail, those inserts have to land in the same transaction. A browser Supabase client can't span a transaction across separate `.from().insert()` calls to different tables — each one is its own request, its own transaction, by design. The only way to get "multiple inserts, one transaction" from React is a function call. So Entry 13's own mechanism, read carefully, doesn't rule out the frontend calling an RPC — it just means the RPC's internal inserts still go through the same trigger, not around it.

**Direct client calls, all enforcement in RLS + triggers** is what's built today and what Module 5 of the study plan organizes the whole project around — Postgres reached directly, no server in between, RLS as the only defense layer. Correct and sufficient for every single-table write already governed by one derive-or-validate trigger. Where it doesn't yet live up to its own principle: clinic_id on staff-submitted writes (visits, complaint_courses, packages) validates against the patient's access, never the submitting staff member's own clinic — you've logged this gap yourself in module_2_logs.md. Closing it the direct-client way means one more parallel derive-from-auth.uid() trigger on top of a surface that's already produced real, shipped bugs: the alphabetical invoice-ordering bug, the no-op derive_clinic_id_from_patient regression, the first-visit deadlock, the missing UPDATE coverage on complaint_courses.

**RPC** doesn't replace any of that — a function's own INSERT statements fire the same triggers a client-issued INSERT would, deferred constraint trigger included. What it adds: one place to resolve auth.uid() into the submitting staff member's real clinic_id and role, once, instead of trusting whatever clinic_id got sent across several separate calls. And, per the reasoning above, it's the only realistic way to get the multi-statement transaction Entry 13's trigger — and, as axis 2 gets into, the session mechanism — actually need.

**A separate API layer** either runs alongside RLS+triggers, meaning the same tenancy rule lives in two places with nothing forcing them to agree, or runs on the service role, bypassing RLS, meaning re-implementing eleven-plus already-debugged triggers' worth of tenancy logic in application code. Worth naming honestly since this is your job-search artifact: a Node API layer reads as more immediately familiar on a portfolio than SECURITY DEFINER functions and deferred constraint triggers, even though the trigger-based approach is the more sophisticated thing to have actually built. But you told me this needs to work with the sessions mechanism and the deferred invoice trigger, not around them — a full API layer replacing them is exactly working around them.

**Recommendation:** direct client calls stay for patients, patient_alerts, patient_vitals, clinical_notes, timeline_events, and complaint_courses — nothing here changes what's already correct. RPC specifically for the two clusters axis 2 identifies as needing one transaction each.

## Axis 2 — when writes fire relative to the workflow

This is Entry 26 in specialty-decision-log.md, almost word for word — Entry 15's session_id mechanism ("omitted on the first insert of a new checkout... echoed back by the frontend on subsequent inserts within the same UI pass") was written without ever pinning down whether the underlying visits/treatment_events writes are progressive or coordinated, and Entry 26 explicitly hands that exact question to "a dedicated follow-up chat" for "the broader frontend↔backend communication question" — this one. So this axis isn't background here, it more or less is the open question. Here's an actual answer.

**Progressive** — a visits or treatment_events row written the instant a procedure gets checked off — collides directly with the four-bucket same-day dedup logic in handover-fee-computation.md: whether the exam fee or lapse penalty applies depends on whether a row is the first billing touchpoint of the day, checked against other visit rows already written. Progressive writes make that an artifact of click order, possibly before the receptionist has finished deciding which complaints are in today's session. And this schema has no status/lifecycle column on visits — "row exists = complete and paid, no status lifecycle," stated flatly, more than once. A progressively-written, later-abandoned row isn't a lost form draft; it's a real-looking billed encounter to daily_ledger and everything downstream, with nothing marking it unfinished. Entry 26 makes the orphaned-row point directly.

**One coordinated write** matches "row exists = complete and paid" exactly, and Entry 26 leans this way for reasons that line up with what's already decided elsewhere: the deferred constraint trigger, write-once invoices, no-draft Pay Later. Where I'd go further than Entry 26 does: I don't think it's one coordinated write, I think it's two, and Entry 8 is why.

Entry 8 explicitly decouples the invoice boundary from the session boundary — "invoicing can follow its own boundary — whatever the receptionist has queued up at the moment 'Create Invoice' is clicked, optionally including an earlier same-day uninvoiced visit if they choose to consolidate." That has a real consequence here: the clinical record (session, visits, visit_services, treatment_events and their complaint links) and the billing record (invoice, invoice_line_items) are allowed to close at different moments. So the honest resolution is two atomic commits, each its own RPC, each its own transaction — one closing out the clinical side of a submission batch, a separate one closing out an invoice, which may reference visits from a session that already committed earlier. For the MVP flow as FRONTEND_WORKFLOW.md documents it today, with no separate "close session without invoicing" action anywhere in the five steps, these two would almost certainly fire back-to-back from the same "Create Invoice" click in practice — but they're structurally two calls, not one, because Entry 8 already opened the door to them happening apart, and there's no reason to build the near-term version in a way that forecloses it.

That reframes Entry 15's mechanism, doesn't contradict it. "Omitted on the first insert... echoed back by the frontend" reads, as written, like separate browser round trips. Under a coordinated model that's not what happens over the network — it happens inside the session-commit RPC's own function body. The RPC receives the whole set of visits/treatment_events the receptionist just confirmed. Internally it inserts the first one with session_id left null — same BEFORE INSERT trigger fires, creates the session row, sets session_id on that row — captures the id into a local variable, and explicitly sets it on every subsequent INSERT it performs in the same call. Same mechanism Entry 15 already specified, just running inside one function's control flow instead of across separate fetch calls.

**Recommendation:** two coordinated commits, not one, not progressive. Session-commit (session + visits + visit_services + treatment_events + treatment_event_links) as one RPC, fired when the receptionist confirms Procedure Logger. Invoice-commit (invoices + invoice_line_items) as a separate RPC, fired at "Create Invoice," referencing already-committed visits/treatment_events rather than creating them. complaint_courses stays outside both — direct client write, early, unchanged. This is my proposed resolution to Entry 26, not a restatement of it — it wants your sign-off before it moves from OPEN to DECIDED.

## Axis 3 — how the frontend learns what the backend did

Two different questions live inside this axis and want different mechanisms: what did my own action just cause, versus what did some other actor change that I need to find out about. Session ids, invoice numbers, auto-provisioned patient_clinic_access rows — your three named examples — are all the first kind.

**Response payload** is the right mechanism for that first kind, and Entry 15 already assumes it — "server creates a session... returns the new id" is response-payload delivery, stated as the mechanism, not something I'm proposing new. Under the axis-2 recommendation, the session-commit RPC hands back the session id in its own return value; the invoice-commit RPC hands back the real invoice_number the same way, replacing the hardcoded `INV-2026-0306-088` placeholder Invoice & Payment currently shows before any write has happened.

**Polling** doesn't have a real use case here that response-payload or real-time already covers better.

**Real-time** — you asked me to say explicitly whether it's warranted, so: no, not as a general mechanism, but there's one legitimate case — the Daily Ledger, if more than one receptionist at the same location has it open at once, which is exactly the "some other actor changed something" case real-time exists for. At this clinic's real scale — a handful of front-desk staff per location, not a high-concurrency app — I'd start cheaper: refetch the ledger on window focus, a short interval, and right after this client's own write succeeds. That covers a receptionist missing a colleague's very recent check-in without standing up and maintaining a realtime subscription. Keep real-time in reserve for the ledger specifically if that's not enough in practice — costs nothing to defer.

One dependency worth naming: if FRONTEND_WORKFLOW.md's Decision 3 (the Waiting/In Therapy/Paid badges, currently unbacked by any schema — daily_ledger hardcodes `'Complete'`) ever gets a real status column, a shared live-updating status becomes a genuine feature worth real-time backing, not just a nicety. Not decided, so I'm not assuming it.

Separately, outside the OPD-visit flow this is scoped to: the pending-to-approved override flow in business-rules-log.md §7 — a receptionist requests a waiver, an admin approves it later from their own session — is a genuinely stronger real-time-or-polling candidate than the ledger. Flagging it, not resolving it.

## Axis 4 — how backend rejections become usable

Module 10 already frames this correctly and deliberately stops short of designing it: a trigger's raise exception is Postgres refusing a write on purpose, arriving through Supabase's client as a structured error — code, message, sometimes a hint — with the actual catching code explicitly deferred to when you're "wiring up real forms against real tables." That's now.

Concrete finding: every trigger in supabase_migration.md that raises an exception — validate_visit_clinic_id, process_new_complaint_course, validate_owner_is_admin, process_new_invoice, validate_invoice_clinic_id, validate_clinic_id_from_access — uses a plain `raise exception 'text with %', value`, no ERRCODE set. Postgres gives all of them the same generic SQLSTATE, P0001. Right now the only way to tell a cross-chain violation apart from a missing-access-record apart from a non-admin owner_id is pattern-matching the message string. That's fragile in a way this project's own history makes concrete: backend-schema-iterations.md already had to correct two code snippets that had drifted from what the real trigger actually does — not error messages specifically, but the same underlying risk, a written description quietly diverging from actual behavior with nothing forcing them to stay in sync. A renamed or reworded raise exception message would break string-matched frontend logic the same silent way. Entry 13's new deferred trigger, once built, would be one more raise exception with the same default code unless it's built differently from the start.

Fix: give each rule family its own SQLSTATE via `raise exception ... using errcode = '<5-char code>', message = '...'` — cross-chain tenancy, missing access record, owner-is-admin, override authorization, and Entry 13's ghost-invoice/line-item mismatch, each its own code. Exactly how you bucket them is a naming call, yours to make. Then one frontend function that takes a PostgrestError and dispatches on `error.code` first, message-matching only as fallback for whatever hasn't been migrated, mapping each known code to a receptionist-readable line — Module 10's own example, "this patient isn't registered at this clinic yet," is the right register. Fold RLS `WITH CHECK` denials into the same function once real policies replace `v1_allow_all` — same generic-error problem, no reason to build a second layer later. Deferred timing doesn't need special handling: from the client's side it's invisible, still one error on whichever call finalizes the transaction — under axis 2's recommendation, that's one of exactly two RPC call sites for the whole clinical flow, not error handling scattered across three screens.
